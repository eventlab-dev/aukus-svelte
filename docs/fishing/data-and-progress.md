# Данные и прогресс

## Виды рыб

`fish/species.ts` — `FishSpecies`: id, имя, вес, speed, resistance, tint, tier,
area, behavior, окна, погода. Спавн-вес в виде не хранится: его несёт класс
редкости, поэтому поля `weight` у вида больше нет. Ростер разбит по водоёмам:
`roster-lake.ts` (12), `roster-river.ts` (12), `roster-sea.ts` (16) → `roster.ts`.

- `tiers.ts` — `TIER_WEIGHTS` (base вне окна / bonus в окне), `TIER_SHINY`,
  `TIER_SHARE`. Четыре класса: common 16, uncommon 12, rare 8, mythic 4.
- Окна и погода больше не фильтруют поклёвку: `isFishInWindow` только решает,
  какой вес взять (см. `gameplay.md`).
- `temperament.ts` — фиксированный характер каждого вида.
- `labels.ts` — окна, погода, описание для кодекса.
- `validate.ts` — `validateFishData`; вызывается на dev-boot.

## Жемчуг

- `fish/pearls.ts` — 12 сортов первого сета: id, имя, сорт 1–5, диапазон
  размера в мм, вес дропа и диапазон `seed` для оттенка. Там же `PEARL_EDGES`,
  `pearlBand()`, `rollPearl()`, `pearlScale()`, `formatFlaw()`/`formatPearlSize()`.
  Спрайты — `pearls-sheet.png` на CDN (12 ячеек 16×16 в порядке `PEARLS`); ракушка
  по-прежнему рисуется кодом.
- `rollFlaw()` — индекс `float` идёт кривой `1 - U^2.5` в меловой конец; зона
  удачи бросает дважды и оставляет лучший. Аура в шейдере привязана к
  зеркальному поясу (`wMirror`), а не к сорту, так что «беспорочность» — это и
  есть её частота (0.40 % на пойманную ракушку, 0.80 % с зоной удачи).
- `fish/shell.ts` — `SHELL_SPECIES`. Ракушка не входит в `FISH`, поэтому не
  считается видом кодекса, не влияет на доли редкости и не проверяется
  `validateFishData`. Она предлагается как поклёвка на любом водоёме
  (`CastFlowState.beginBite`, шанс `PEARL.shellChance`), а после поимки
  выдаёт жемчужину.
- `game/pearl/` — пиксель-арт (`art.ts`), универсальный шейдер и спрайт
  (`PearlView.ts`), постановка раскрытия (`PearlReveal.ts`).
- Рекорд жемчужины — лучший экземпляр по меньшему `float`, затем по большему
  размеру. Цены/экономики в игре нет, поэтому «дороже» выражено индексом, размером и диапазоном блеска.

## ProgressSnapshot

```ts
interface ProgressSnapshot {
	version: 6
	selectedArea: 'cove' | 'deep' | 'rapids'
	fish: Record<string, { caught: number; bestKg: number; lightestKg: number; shiny: boolean }>
	pearls: Record<string, { caught: number; best: { float: number; seed: number; sizeMm: number } }>
	areaCatches: Record<'cove' | 'deep' | 'rapids', number> // уловы рыб на водоёме
	lessons: string[] // id страниц справки, которые игрок уже видел
	updatedAt: number
}
```

`areaCatches` — счётчик уловов рыб на водоёме, топливо pity: для каждого
непойманного вида вес умножается на `min(1.5^floor((c−100)/20), 4)`
(`pityMultiplier` в `game/castPick.ts`). Ракушки в счётчик не идут, отдельного
флага «вид пойман» нет: `fish[id].caught > 0` и есть `is_caught_before`.

`lessons` — просмотренные уроки обучения (`HelpPageId` из `texts.ts`: `cast`,
`fight`, `counter`, `land`). Записка механики открывается один раз за документ:
без этого списка перезагрузка возвращала все уроки заново. `markLessonSeen`
пишет документ сразу, не через общий дебаунс, — закрытая записка не должна
вернуться после F5. Неизвестные id при чтении отбрасываются.

`bestKg` и `lightestKg` — два конца личного рекорда вида: рекордно тяжёлый и
рекордно лёгкий экземпляр. Оба конца видит кодекс: карточка записи печатает их
двумя подписанными строками (корона — тяжёлый, стрелка — лёгкий), а слот
ростера — только счётчик. `shiny` — найден ли у вида шайни-окрас: флаг
не сбрасывается, и справочник продолжает показывать редкий экземпляр, а не
последний улов. Платиновая рамка слота (`fish/platinum.ts`) — производная от этих
же полей: целевое число поимок по классу и оба конца веса; `shiny` в условие не
входит и остаётся отдельной отметкой кодекса, поэтому отдельного признака в
документе нет и правило можно менять, не мигрируя сохранения.

`ProgressTracker` дебаунсит сохранение (500 мс), сериализует записи и повторяет при
ошибке. `flushProgress()` форсирует отправку.

`ProgressRepository` — `load(): Promise<unknown>`, `save(snapshot): Promise<void>`.
Готовые адаптеры: `LocalProgressRepository`, `MemoryProgressRepository`,
`createHttpProgressRepository`. Публичный API — `src/lib/minigames/fishing/engine/index.ts`.

## Расписание погоды

`WorldStore` (`<prefix>:world:v1`) хранит `WorldData`:

```ts
interface WorldData {
	weather?: Record<string, string> | string // legacy: id фронтов по водоёмам
	areas?: Record<string, SavedArea> // расписание
}
interface SavedArea {
	current: SavedFront
	queue: SavedFront[] // очередь, которую рисует полоса прогноза
}
interface SavedFront {
	id: string
	endsAt: number // epoch-секунды, когда фронт заканчивается
	length: number // полная длительность, секунды (480–720)
}
```

`WorldClock` восстанавливает очередь по `length`, при загрузке догоняет истёкшие
фронты и пишет обе формы: `areas` для этого билда, `weather` — чтобы сборка без
расписания прочитала то же небо. Иды фронтов — `WeatherId` из `types.ts`; новый
`aurora` сохраняется как любой другой, а `savedWeatherId` переводит исторические
`rain`/`storm` в `snow`/`blizzard` и отбрасывает всё, чего нет в `WEATHER`.

## Ключи localStorage

| Ключ                   | Что                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------ |
| `<prefix>:progress:v1` | прогресс справочника и выбранный водоём                                              |
| `<prefix>:settings:v1` | mute, dev-оверрайды микса                                                            |
| `<prefix>:world:v1`    | расписание погоды: текущий фронт (`endsAt`, `length`) и очередь прогноза по водоёмам |

`prefix` по умолчанию `fishing-game`, переопределяется опцией `storagePrefix`.
Маршрут `src/routes/minigames/fishing` передаёт `aukus5-fishing`, поэтому в браузере
ключи выглядят как `aukus5-fishing:progress:v1` и т. д.

## Миграции

- id водоёмов исторические: `deep` (озеро), `rapids` (река), `cove` (море);
  не переименовывать.
- старые погодные id `rain`/`storm` переводятся в `snow`/`blizzard` в
  `world/WorldClock.ts`.
- старый `world:v1` (строка или карта id) читается как fallback: фронт после
  обновления начнётся заново, потому что времён в нём не было; начиная с первого
  сохранения прогноз уже переживает перезагрузку.
- `parseProgress` чистит неизвестные поля и битые записи; версия схемы — 6.
- v2 → v3: добавлено поле `pearls`; старый документ читается с пустой
  коллекцией жемчуга, при следующем сохранении версия становится 3. Записи
  неизвестных сортов и битые `best` отбрасываются.
- v3 → v4: у записи рыбы появились `lightestKg` и `shiny`. В старом документе
  известен только самый тяжёлый экземпляр, поэтому `lightestKg` при чтении
  становится равным `bestKg` (а не нулём, иначе первый же улов вида навсегда
  закреплял бы «рекордно лёгкую» запись на 0 кг), `shiny` — `false`.
- v4 → v5: добавлено поле `lessons`. Старый документ читается с пустым списком,
  поэтому после обновления обучение показывается ещё раз — по одному разу на
  механику, — а дальше уже не возвращается.
- v5 → v6: добавлено поле `areaCatches` (счётчик pity). В старом документе его
  нет, поэтому он собирается из кодекса: сумма `caught` по видам каждого
  водоёма. Это лучшее приближение — документ не знал, где именно ловили, — и
  оно честнее нуля: игрок со 120 плотвой уже отловился на этом озере.
  Неизвестные ключи водоёмов и отрицательные значения отбрасываются.

При изменении схемы добавляйте миграцию в `progress.ts` и обновляйте этот документ.
